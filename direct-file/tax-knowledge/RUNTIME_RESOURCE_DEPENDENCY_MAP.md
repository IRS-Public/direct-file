# Runtime Resource Dependency Map

This map answers which checked-in runtime resources are tax-source dependent and whether they should be generated by the tax knowledge pipeline.

Inspected roots:

- `backend/src/main/resources`
- `tax-advisor/src/main/resources`

The machine-readable map lives in `runtime-resources/direct-file-resource-map.yaml`.

## Summary

| Resource group | IRS-source dependency | Pipeline generation posture |
| --- | --- | --- |
| `backend/src/main/resources/tax/*.xml` | Direct | Generate draft patches from reviewed rules, source chunks, MeF material, and scenarios |
| `backend/src/main/resources/pdf/<year>/<form>/<lang>/configuration.yml` | Direct | Generate draft PDF field maps with PDF extraction, source citations, fact-path matching, and review |
| `backend/src/main/resources/factgraphservice/xmlFactPaths` | Derived | Regenerate mechanically from approved fact graph XML |
| `tax-advisor/src/main/resources/tax-plan/*.xml` | Direct | Generate draft planning graph patches from reviewed rules and scenarios |
| `backend/src/main/resources/data-import-gating-sample.json` | Indirect | Generate or validate from evidence maps, conflicts, import support policy, and provider contracts |
| `backend/src/main/resources/dataimportservice/mocks/*.json` | Indirect | Generate synthetic fixtures from reviewed scenarios and provider contracts |
| `backend/src/main/resources/tax/FactDictionaryModule.rng` | Platform | Validate generated XML against it; do not generate from IRS sources |
| DB migrations, app config, logging, PMD, banner | None | Keep outside the tax corpus pipeline |

## Key Finding

The pipeline can produce fact graph artifacts, but the current checked-in pipeline is still a draft-authoring pipeline. It creates source chunks, relevance classifications, rules, evidence maps, conflicts, scenarios, and fact graph work items. It does not yet emit final approved runtime files directly into `backend/src/main/resources/tax`, `backend/src/main/resources/pdf`, or `tax-advisor/src/main/resources/tax-plan`.

The correct next step is to add reviewed emitters that produce draft patches for those runtime files. Those emitters should never rely on IRS publications alone. They need the broader IRS corpus:

- forms and instructions for line structure and worksheets
- publications for definitions, examples, eligibility explanations, and procedural details
- revenue procedures, notices, or official IRS pages for annual constants
- MeF schemas and business rules for export names, e-file constraints, and validations
- Direct File product-scope decisions for unsupported cases and blockers

## Fact Graph XML

Files:

- `backend/src/main/resources/tax/*.xml`
- `tax-advisor/src/main/resources/tax-plan/*.xml`

These are the main tax-source-dependent runtime artifacts. The backend currently has 36 tax XML modules, and the plan service has one planning XML module.

The pipeline should generate these as source-backed work items first:

- fact paths added or changed
- writable facts and their types
- derived calculations and dependencies
- constants and tax-year-scoped values
- validations and blockers
- MeF export mappings
- source references and scenario coverage

Generation confidence varies by artifact type:

- High: annual constants, line-to-line sums, simple thresholds, mechanical fact indexes.
- Medium: worksheets, eligibility trees, filing-status interactions, e-file business rule translations.
- Review-required: product-scope blockers, user-facing applicability gates, simplified planning models, and inferred fact-path design.

## PDF Configurations

Files:

- `backend/src/main/resources/pdf/<year>/<form>/<lang>/configuration.yml`

There are currently 76 PDF configuration files across tax years 2024 and 2025.

These depend directly on IRS form PDFs and approved fact paths. A generator can draft them by combining:

- PDF field names from fillable form metadata
- page text and line labels from PDFBox extraction
- optional vision/OCR extraction where form metadata or text extraction is weak
- source chunks for form instructions and line semantics
- fact graph XML inventory for candidate fact paths

The output should be a review packet plus a patch, not an automatically approved runtime config.

## Derived Indexes

File:

- `backend/src/main/resources/factgraphservice/xmlFactPaths`

This is a derived artifact. It should be regenerated from approved fact graph XML after generation or manual edits. It should not require direct IRS source review, but the source fact graph XML that feeds it does.

## Data Import Artifacts

Files:

- `backend/src/main/resources/data-import-gating-sample.json`
- `backend/src/main/resources/dataimportservice/mocks/*.json`

These are indirectly tax-source dependent. The IRS corpus helps define what a document means, which topics it may trigger, and which contradictions should be detected. Provider payload contracts and Direct File support policy are also required.

The pipeline should generate these from `evidence`, `conflicts`, and `scenarios`, then validate them against provider schemas and backend tests.

## Out Of Scope For Corpus Generation

These resources should not be generated from IRS publications:

- `backend/src/main/resources/db/**/*.yaml`
- `backend/src/main/resources/application*.yaml`
- `backend/src/main/resources/logback*.xml`
- `backend/src/main/resources/banner.txt`
- `backend/src/main/resources/pmd/static-analysis-ruleset.xml`
- `tax-advisor/src/main/resources/application*.yaml`
- `backend/src/main/resources/tax/FactDictionaryModule.rng`

They may change to support the pipeline, but their authority is application architecture, not the IRS corpus.
